Phase 1: Rust Through Pixels
Week 0 (soft start) + Weeks 1–3 · The language and the borrow checker, learned by building an image library
GOAL: Get the toolchain working and write a real image file with zero dependencies. No timer.
You already program well — Rust's syntax will feel familiar; only ownership is new. Use Week 0 to set up and to get the idea of what an image actually is into your hands.
SETUP (1 HR)
Install the toolchain via rustup (rustup.rs) — gives rustc, cargo, and std. Verify with `rustc --version` (you want 1.85+ for the 2024 edition). Run `rustup component add clippy`.
Wire up Zed for Rust: rust-analyzer ships built in. Turn ON inlay type hints and format-on-save — seeing inferred types everywhere is a huge aid while ownership is still new. Your vim keymap carries over untouched.
Create a PUBLIC GitHub repo "pixlab" — this is your portfolio repo, not a scratch pad. README: "An image processing library written from scratch in Rust — filters, resampling, a toy JPEG encoder, a serving pipeline, and a browser editor."
`cargo new pixlab && cd pixlab && cargo run`. Open Cargo.toml — note `edition = "2024"`. This is your project manifest (like pyproject/package.json).
Bookmark what you'll live in: the Book (Brown interactive edition, rust-book.cs.brown.edu), Rustlings, the std docs, and docs.rs/image — you'll read the image crate's source as often as you use it.
THURSDAY — FIRST TASTE (1–2 HRS)
📗 LEARN: Book Ch. 1–3 (setup, guessing game, common concepts). The guessing game is a fast tour of match, Result, crates, and shadowing.
🔥 DRILL: `cargo install rustlings`, then `rustlings init`. Do the intro + variables sections.
🎯 INTERVIEW: Write down the mental model you'll use for eight weeks — an image is a width, a height, a pixel format, and ONE flat buffer in row-major order. The byte offset of channel c at (x, y) is `y*stride + x*channels + c`, and stride ≥ width*channels because rows are often padded for alignment. Almost every image bug you will ever write is a stride bug.
FRIDAY — OWNERSHIP + FIRST IMAGE (1–2 HRS)
📗 LEARN: Book Ch. 4 (Ownership) — slowly. Move semantics, borrowing, slices. This is THE chapter and the only genuinely new idea coming from Python. Don't rush it.
🔒 BUILD: Write a PPM (P6) file with NO crates — a 256×256 RGB gradient. Header is literally `P6\n{w} {h}\n255\n` followed by raw RGB bytes. Open the result in Preview/GIMP/ffplay. You just wrote an image format. Push it.

THE MAKE-OR-BREAK WEEK: everything else depends on ownership, so you learn it inside a real Image struct rather than in toy exercises. Expect to fight the compiler — that's the learning.
MONDAY — OWNERSHIP DEEP (2.5 HRS)
📗 LEARN: Re-read Book Ch. 4 and take the Brown edition quizzes — they're built to catch the exact misconceptions beginners have. Make move vs copy vs clone crystal clear.
🔥 DRILL: Rustlings `move_semantics` (all exercises).
🔒 BUILD: `struct Image { data: Vec<u8>, width: u32, height: u32, format: PixelFormat }`. Write `new(w, h, fmt)` (zero-filled) and `from_raw(...) -> Result<Image, _>` that validates `data.len()` against the expected size. Notice the API question this forces: a filter taking `self` consumes the image, one taking `&mut self` mutates in place, one taking `&self` allocates a new one. That choice IS your library design.
🔒 BUILD: Start a "Rust" Anki deck. First cards: when does a value move vs copy? what is a borrow? why can't a `&mut` coexist with a shared `&`?
TUESDAY — REFERENCES & SLICES (2.5 HRS)
📗 LEARN: Book Ch. 4.2–4.3 (references, slices). Internalize the aliasing rule: one `&mut` XOR many `&`. This single rule is why Rust prevents data races — and in Week 4 it's what lets you hand out disjoint image tiles to threads with no locks at all.
🔥 DRILL: Rustlings `primitive_types`, `vecs`, `strings` — these force the `&str` vs `String` distinction, the #1 early friction point.
🔒 BUILD: Row access built on slices: `fn row(&self, y: u32) -> &[u8]` and `row_mut`, both implemented over `chunks_exact(self.stride())`. Then `pixel(x, y) -> &[u8]`. Rule for the whole sprint: take `&[u8]`, never `Vec<u8>`, in a signature that only reads.
WEDNESDAY — STRUCTS, ENUMS & MATCH (2.5 HRS)
📗 LEARN: Book Ch. 5–6 (structs, methods, enums, match, Option). Coming from Python, `Option<T>` replacing null is the key shift — the compiler forces you to handle "nothing".
🔥 DRILL: Rustlings `structs`, `enums`, `options`.
🔒 BUILD: `enum PixelFormat { Gray8, GrayAlpha8, Rgb8, Rgba8, Rgb16 }` with `channels()`, `bytes_per_channel()`, and `has_alpha()` dispatched by match. Add `enum ColorSpace { Srgb, LinearRgb }` — Friday explains why you need it, and why libraries that omit it produce subtly wrong output forever.
THURSDAY — LIFETIMES VIA IMAGE VIEWS (2.5 HRS)
📗 LEARN: Book Ch. 10.3. Lifetimes are NOT about how long values live — they're labels relating references so the compiler can prove nothing dangles. Then watch Jon Gjengset's "Crust of Rust: Lifetime Annotations", the best explanation anywhere.
🔥 DRILL: Rustlings `lifetimes`.
🔒 BUILD: `struct View<'a> { data: &'a [u8], x: u32, y: u32, w: u32, h: u32, stride: usize }` — a borrowed sub-image, i.e. a crop with no copy — plus a `rows()` iterator over it. This is exactly how real libraries expose a region of interest, and it's the most natural lifetime exercise you will find.
FRIDAY — COLOR, LUMA & THE GAMMA TRAP (2.5 HRS)
📗 LEARN: RGB → grayscale is not the average of three channels. Rec.601 luma is 0.299R + 0.587G + 0.114B; Rec.709 (HD, matching sRGB primaries) is 0.2126R + 0.7152G + 0.0722B. Green dominates because your eye does.
📗 LEARN: Now the trap. sRGB byte values are gamma-encoded (roughly a 2.2 power curve), so they are NOT proportional to light. Averaging, blurring, resizing, or alpha-compositing them directly is mathematically wrong. The correct sequence is always: decode to linear → do the math → re-encode to sRGB.
🔒 BUILD: Write `to_gray()` twice — naive (weights applied to raw sRGB bytes) and correct (linearize, weight, re-encode). Save both and diff them. The naive version is visibly darker through the midtones. Keep both in the repo; that diff image is a better interview answer than any explanation.
🎯 INTERVIEW: Anki — "why aren't the luma weights equal?", "what does gamma encoding buy you at 8 bits per channel?", "name three operations that are wrong when performed in sRGB space" (resize, blur, alpha compositing).
SATURDAY — PROJECT: PIXLAB CORE (3 HRS)
Saturday project — a working `pixlab` library plus CLI. Use the `image` crate to DECODE PNG/JPEG only; everything after decode you write yourself over your own `Image` type: grayscale (both variants), invert, brightness/contrast, and threshold. README with before/after images and a note on the gamma difference. Every week from here builds on this crate.

THE CONVOLUTION WEEK: traits give you a composable filter pipeline, and convolution gives you blur, sharpen, and edge detection out of a single loop — plus the cleanest complexity story in the whole plan.
MONDAY — GENERICS (2.5 HRS)
📗 LEARN: Book Ch. 10.1 (generics + monomorphization). Generic functions, structs, enums, and the zero-cost story — generics compile to specialized code.
🔥 DRILL: Rustlings `generics`.
🔒 BUILD: Make the buffer generic over sample type: `Image<T>` for `T: Copy + Default`, so u8, u16, and f32 images share one implementation. f32 matters more than it looks — intermediate filter results want float precision, and HDR/16-bit sources are common. Notice exactly where you now need trait bounds you didn't need before.
TUESDAY — TRAITS & DISPATCH (2.5 HRS)
📗 LEARN: Book Ch. 10.2 + Ch. 17. Traits are interfaces. Trait bounds, `impl Trait`, and `dyn Trait` (dynamic dispatch) vs generics (static dispatch). Meet the core derives: Debug, Clone, PartialEq, Eq, Hash, Default.
🔥 DRILL: Rustlings `traits`.
🔒 BUILD: `trait Filter { fn name(&self) -> &str; fn apply(&self, src: &Image) -> Result<Image, ImageError>; }`, then `struct Pipeline { stages: Vec<Box<dyn Filter>> }` that runs them in order. Dynamic dispatch is genuinely the right call here — the stage list is assembled from CLI arguments at runtime, so you can't monomorphize it.
🎯 INTERVIEW: Anki — "static vs dynamic dispatch, when does the vtable cost actually matter?", "when does monomorphization blow up compile time and binary size?" You now have a real example of each in one codebase.
WEDNESDAY — ERROR HANDLING (2.5 HRS)
📗 LEARN: Book Ch. 9 (Result, the `?` operator, panic vs recoverable). Then the ecosystem standard: `thiserror` for libraries (derive your error enum) and `anyhow` for applications. This is how real Rust handles errors — no exceptions.
🔥 DRILL: Rustlings `error_handling`.
🔒 BUILD: `enum ImageError { DimensionMismatch{..}, UnsupportedFormat(..), KernelNotOdd(..), Io(#[from] std::io::Error) }` via thiserror, propagated with `?`. Hard rule: the library never panics, only `main` does. Image inputs are hostile — truncated files, absurd dimensions, wrong channel counts — and that's exactly the code an interviewer will poke at.
THURSDAY — CONVOLUTION, PART 1 (2.5 HRS)
📗 LEARN: A kernel is a small weight matrix slid over the image; each output pixel is a weighted sum of its neighborhood. Box blur, Gaussian blur, sharpen (identity plus an edge term), and Sobel Gx/Gy for gradients are all the same loop with different weights. Two things break naive implementations: normalization (weights must sum to 1 or you shift overall brightness) and border handling (clamp / reflect / wrap / crop — pick one, document it, be consistent).
🔒 BUILD: `fn convolve(src: &Image, kernel: &[f32], k: usize, border: Border) -> Image` — the naive O(w·h·k²) version. Get Gaussian blur working, then Sobel edge magnitude as `sqrt(gx² + gy²)`.
FRIDAY — CONVOLUTION, PART 2: SEPARABILITY (2.5 HRS)
📗 LEARN: A 2D Gaussian is the outer product of two 1D Gaussians, so one horizontal pass followed by one vertical pass gives an identical result in O(w·h·2k) instead of O(w·h·k²). At radius 15 that's roughly a 7.5× cut in multiplies for free. Box blur goes further: a sliding running sum makes it O(1) per pixel regardless of radius, and three box passes approximate a Gaussian closely — which is what most "fast blur" implementations in the wild actually are.
🔒 BUILD: Implement the separable Gaussian and the running-sum box blur. Assert the separable output matches the naive output within float epsilon — that test is the whole point.
🎯 INTERVIEW: This is a sliding-window problem, the same pattern you've been drilling on LeetCode, in two dimensions. Practice deriving O(k²) → O(2k) → O(1) out loud at a whiteboard, and be able to say which technique buys which.
SATURDAY — PROJECT: FILTER LIBRARY + BENCHMARKS (3–4 HRS)
Saturday project — finish the filter set (blur, sharpen, Sobel, emboss, median) behind the `Filter` trait, wire the CLI to compose them (`pixlab in.jpg -f blur:5 -f sobel out.png`), and benchmark naive vs separable vs running-sum with `criterion` on a 4K image. README with the complexity table and the real numbers next to it. A genuine portfolio centerpiece.

READING-FLUENCY WEEK AND THE RESIZE WEEK: iterators are how idiomatic Rust is written, and resampling is the image topic most likely to come up in a real product interview.
MONDAY — CLOSURES & ITERATORS (2.5 HRS)
📗 LEARN: Book Ch. 13. Fn/FnMut/FnOnce, the Iterator trait, map/filter/fold/collect. Iterators are lazy and `collect()` is type-driven — that part is new versus Python comprehensions, but it clicks fast.
🔥 DRILL: Rustlings `iterators` (all — they're meaty and worth it).
🔒 BUILD: Rewrite your per-pixel filters as iterator chains over `chunks_exact(channels)` and `zip`. Then benchmark against the indexed-loop version: `chunks_exact` gives the optimizer a known-length slice, so bounds checks frequently vanish in a way indexed access can't guarantee. That's a measurable performance reason to write idiomatic Rust, not just an aesthetic one.
TUESDAY — SMART POINTERS & COW (2.5 HRS)
📗 LEARN: Book Ch. 15 (Box, Rc, RefCell, Deref, Drop). When you need heap allocation (Box), shared ownership (Rc), or interior mutability (RefCell) — and why `Rc<RefCell<T>>` exists.
🔥 DRILL: Rustlings `smart_pointers`, `box`.
🔒 BUILD: Use `Cow<'_, [u8]>` for a stage that may return its input untouched — a resize whose target dimensions already match, or a format conversion that's a no-op. You skip the copy without changing the signature. Images are big; a needless clone of a 4K RGBA buffer is 33 MB.
🎯 INTERVIEW: Anki — "Box vs Rc vs RefCell vs Cow, what does each buy you?", "what is interior mutability and when is it a smell?"
WEDNESDAY — MODULES, CRATES, WORKSPACES (2.5 HRS)
📗 LEARN: Book Ch. 7 (modules, paths, pub, use) + Ch. 14 (Cargo, workspaces, publishing).
🔒 BUILD: Split into a Cargo workspace: `pixlab-core` (pure buffer math, no I/O, no CLI, minimal dependencies), `pixlab-cli`, and stubs for `pixlab-server` and `pixlab-wasm`. Keeping core dependency-free is not architecture theater — it's the reason your WASM binary in Week 7 will be small. Add `///` doc comments and run `cargo doc --open`.
THURSDAY — RESAMPLING: THE REAL ONE (2.5 HRS)
📗 LEARN: Upscaling and downscaling are different problems. Upscaling is interpolation — nearest (blocky), bilinear (soft), bicubic (sharper, can ring), Lanczos (sharpest, rings most). Downscaling is a sampling problem: you MUST low-pass filter first, because by Nyquist any detail above half the new sampling rate folds back as moiré and crawling edges. Taking every Nth pixel is the classic bug. Area averaging, or a Lanczos window scaled to the destination, fixes it.
📗 LEARN: And resample in linear light, not in sRGB — the same gamma trap from Week 1. Downscaling gamma-encoded values darkens the result, most visibly on fine high-contrast detail. This is why a naive thumbnail generator makes everything look muddy.
🔥 DRILL: 2–3 LeetCode mediums in Rust to keep the language in your hands. Rotate Image is a good one this week — an in-place transpose plus row reversal is literally an image operation.
🔒 BUILD: Implement nearest, bilinear, and area-average downscale. Downscale a fine checkerboard 8× with each and look at the moiré. Then do it again in linear light and compare.
FRIDAY — TESTING, CLIPPY, FMT, CI (2.5 HRS)
📗 LEARN: Book Ch. 11 (unit tests, integration tests in tests/, #[cfg(test)]). Then run `cargo clippy -- -D warnings` on everything and fix every lint — clippy is the best Rust teacher you have. Finish with `cargo fmt`.
🔒 BUILD: Golden-image tests — compare output against committed reference PNGs with a tolerance, since float math differs across platforms and exact equality will flake. Add GitHub Actions running test, clippy, and fmt --check. A green badge signals professionalism.
🎯 INTERVIEW: Implement PSNR — 10·log10(MAX²/MSE) — as a test helper. You now have a number to answer "did that optimization hurt quality?", and you'll extend it to SSIM in Week 6. Being able to quantify a quality regression is the difference between an opinion and an argument.
SATURDAY — PROJECT: RESIZE + QUALITY REPORT (3–4 HRS)
Saturday project — `pixlab resize` supporting nearest / bilinear / bicubic / Lanczos / area, with a `--linear` flag for gamma-correct resampling. Then generate a comparison contact sheet: one source image downscaled 8× through every filter, sRGB versus linear, with PSNR against a high-quality reference. Put the grid in the README. That single artifact answers "do you actually understand resampling?" before you say a word.

Phase 2: Pipelines & Services
Weeks 4–5 · Parallel batch processing and a deployed image transform service · the Netflix/Airbnb-shaped work
THE THROUGHPUT WEEK: image work is the textbook case of embarrassingly parallel CPU-bound work — and the textbook case of people putting that work on the wrong runtime.
MONDAY — THREADS & SHARED STATE (2.5 HRS)
📗 LEARN: Book Ch. 16. Threads, `move` closures, channels (mpsc), and Arc + Mutex for shared state. The Send and Sync marker traits are WHY the borrow checker turns data races into compile errors.
🔥 DRILL: Rustlings `threads`.
🔒 BUILD: Tile-parallel filtering by hand — split the output buffer with `chunks_mut(rows_per_tile * stride)` and hand each chunk to a scoped thread (`std::thread::scope`). No Mutex, no Arc, no locking: the borrow checker proves the tiles are disjoint. This is the Week 1 aliasing rule paying rent, and it's a great thing to be able to explain.
TUESDAY — RAYON & SCALING LIMITS (2.5 HRS)
📗 LEARN: rayon — work-stealing data parallelism where swapping `iter()` for `par_iter()` is often the entire change. Learn `par_chunks_mut` for image tiles.
🔒 BUILD: Parallelize your convolution with rayon and measure at 1, 2, 4, and 8 threads on a 4K image. Plot the speedup curve.
🎯 INTERVIEW: Explain your own curve with Amdahl's law — and know why it flattens earlier than core count suggests. For a blur you're usually memory-bandwidth bound, not compute bound: the kernel reads far more bytes than it does arithmetic. "We added cores and it didn't get faster" is a real production story, and this is the reason.
📗 LEARN: Read Ch. 1–2 of Mara Bos's "Rust Atomics and Locks" (free at marabos.nl/atomics) — the clearest account of Send/Sync, Arc, and Mutex internals anywhere.
WEDNESDAY — ASYNC CONCEPTS (2.5 HRS)
📗 LEARN: Book Ch. 17 (async/await) + the async book intro. The model: an `async fn` returns a Future, Futures are LAZY (nothing happens until polled), and you need a runtime to drive them. Concurrency without necessarily any parallelism.
🔥 DRILL: Watch Jon Gjengset's "Crust of Rust: async/await" for the underlying mental model — poll, wakers, the generated state machine.
🎯 INTERVIEW: The rule worth memorizing: never run a CPU-bound image transform directly on an async task. It occupies an executor thread for its whole duration and stalls every unrelated request sharing that thread. Use `tokio::task::spawn_blocking` or hand the work to a rayon pool. Be able to describe the SYMPTOM — latency spikes on endpoints that have nothing to do with images — not just the fix. That's the version of this answer that sounds like experience.
THURSDAY — TOKIO (2.5 HRS)
📗 LEARN: Work through the official tokio tutorial (tokio.rs/tokio/tutorial) — Hello Tokio, Spawning, Shared State, Channels. tokio is THE async runtime. Learn `#[tokio::main]`, `tokio::spawn`, `.await`, and `tokio::select!`.
🔒 BUILD: Fetch 50 image URLs concurrently with `reqwest`, decode each on a blocking pool, and report total wall time against a sequential baseline. Watch where the time actually goes — it's usually decode, not network.
FRIDAY — BACKPRESSURE & BOUNDED CONCURRENCY (2.5 HRS)
📗 LEARN: Unbounded concurrency is a memory bug waiting to happen — fifty simultaneous 8K decodes will OOM a small box, because a decoded 8K RGBA frame is ~130 MB before you've done anything to it. Bound it with `tokio::sync::Semaphore`, bounded `mpsc` channels, or `buffer_unordered(n)` over a stream. Gotcha: holding a `std::sync::Mutex` across an `.await` is a bug — learn exactly why.
🔒 BUILD: Add a semaphore capping concurrent decodes, then throw a burst at it and show the memory ceiling holding flat. Anki — "why are futures lazy?", "std Mutex vs tokio Mutex, when each?", "what does backpressure actually mean?"
SATURDAY — PROJECT: BATCH THUMBNAIL PIPELINE (3–4 HRS)
Saturday project — a CLI that walks a directory and produces derivatives (320 / 640 / 1280 wide, WebP and JPEG) with a bounded worker pool, a progress bar (`indicatif`), per-file error isolation so one corrupt input can't kill the run, and a summary report: files processed, bytes in and out, wall time, throughput. Benchmark it against ImageMagick's `mogrify` on the same set and put the numbers in the README. This is the exact shape of an internal media tool at any company with photos.

THE INTERVIEW WEEK: Airbnb serves listing photos, Netflix serves artwork; both run an image transform-and-delivery pipeline. Build an honest small version and you can answer the design question from experience instead of from a blog post.
MONDAY — AXUM & THE TRANSFORM URL (2.5 HRS)
📗 LEARN: axum — the standard modern web framework, built on tokio + hyper + tower. Routers, handlers, and extractors (Path, Query, Json, State).
🔒 BUILD: `GET /i/:id?w=&h=&fit=cover|contain&fmt=auto|webp|jpeg&q=` serving a transformed image. Keep everything in memory for now; the transform code is already written from Weeks 2–3.
🎯 INTERVIEW: Why you must whitelist dimensions or sign the URL. An open resize endpoint is free CPU exhaustion: every distinct `?w=` value is a guaranteed cache miss plus a full decode, so an attacker walks w=1..2000 and buries your origin. Real services either allow a fixed set of widths or HMAC-sign the parameters. This is the security question inside the design question, and volunteering it lands well.
TUESDAY — SERDE & PARAM NORMALIZATION (2.5 HRS)
📗 LEARN: serde + serde_json — THE serialization framework. `#[derive(Serialize, Deserialize)]`, and how axum's `Json<T>` extractor uses it.
🔒 BUILD: A `Transform` struct that parses, validates, and NORMALIZES params into a canonical form — clamp dimensions to the allowed set, resolve `fmt=auto` against the Accept header, drop defaults, fix parameter order. That canonical form is your cache key. If `?w=640` and `?width=640&h=` produce different keys, your hit rate quietly halves and nobody notices for a year.
WEDNESDAY — CACHING & OBSERVABILITY (2.5 HRS)
📗 LEARN: The cache hierarchy — CDN edge, then your derivative cache, then origin. `Cache-Control: public, max-age=31536000, immutable` for content-addressed derivative URLs; ETag and 304 for everything else. `Vary: Accept` is required when you content-negotiate format, and it fragments the edge cache — that tradeoff is worth being able to discuss. Then structured logging with `tracing` + `tracing-subscriber`.
🔒 BUILD: An on-disk (or `moka` in-memory) derivative cache keyed by the canonical transform, correct cache headers, and tracing spans that time decode, transform, and encode SEPARATELY. Log hit/miss ratio. Knowing which of the three dominates is the difference between guessing and optimizing.
THURSDAY — STORAGE & METADATA (2.5 HRS)
📗 LEARN: Originals live in object storage and are never mutated; derivatives are disposable and regenerable, which is what makes aggressive caching safe. Metadata — dimensions, format, EXIF orientation, dominant color, a placeholder hash — lives in a database. `sqlx` gives you async, compile-time-checked SQL against the real schema (no ORM magic).
🔒 BUILD: SQLite via sqlx with migrations: an `images` table (id, storage_key, width, height, format, bytes, created_at). Populate on upload, serve it at `GET /i/:id/meta`. Add a blurhash/thumbhash placeholder — that's how both companies avoid layout shift while a photo loads, and it's a nice detail to have implemented.
🎯 INTERVIEW: EXIF orientation deserves its own card. A JPEG can be stored rotated with a flag saying "display me rotated", so if you strip metadata during processing without applying it first, every photo from certain phones comes out sideways. It is the single most common image-pipeline bug in production.
FRIDAY — SYSTEM DESIGN WRITE-UP (2.5 HRS)
📗 LEARN: Read how the real ones work — Airbnb's and Netflix's engineering posts on their image and artwork pipelines, plus the architecture docs for imgix, Cloudinary, and Thumbor. Note the decisions that recur everywhere: pre-generate versus on-the-fly, where the CDN sits, how originals are protected, how format negotiation happens.
🔒 BUILD: Write `docs/DESIGN.md` in your own repo answering the prompt end to end — upload → validate (dimension caps, format sniffing rather than trusting extensions, decompression-bomb limits) → store original → derivative strategy → CDN → invalidation → cost. State the tradeoff you'd defend: on-the-fly plus aggressive edge caching for the long tail of sizes, pre-generated for the handful of hot ones.
🎯 INTERVIEW: Rehearse the design out loud in five minutes, then again in sixty seconds. Both lengths get asked, and the short one is harder.
SATURDAY — PROJECT: DEPLOY IT (3–4 HRS)
Saturday project — config via env vars, a multi-stage Dockerfile producing a small final image, a `/health` endpoint, and a deploy to Fly.io / Shuttle / Railway so you have a LIVE URL. Add a tiny demo page using `<img srcset>` to hit your own service at multiple widths. README with an architecture diagram and the link. This is the project that gets you the interview.

Phase 3: Codecs, WASM & Performance
Weeks 6–8 · How compression actually works, Rust in the browser, the hot loop, and a capstone
THE CODEC WEEK: this is the domain knowledge separating "I called the image library" from "I understand the format" — and it doubles as a serious data-structures workout.
MONDAY — COLOR SPACES & CHROMA SUBSAMPLING (2.5 HRS)
📗 LEARN: RGB → YCbCr separates luma (Y) from chroma (Cb, Cr). Human vision has far more luminance resolution than color resolution, so codecs discard chroma first: 4:4:4 keeps everything, 4:2:2 halves chroma horizontally, 4:2:0 halves it in both directions — a 50% data reduction before any other compression has happened. Also learn where color management lives: sRGB versus Display P3, ICC profiles, and what breaks when you strip one.
🔒 BUILD: RGB ↔ YCbCr conversion plus a 4:2:0 subsample/upsample round-trip. Measure the error on a photograph, then on a synthetic image with saturated red text on white. The failure mode — color fringing on hard chroma edges — becomes obvious immediately, and it's why screenshots of text look bad as JPEG.
TUESDAY — THE DCT (2.5 HRS)
📗 LEARN: The 8×8 discrete cosine transform rewrites a block of pixels as a sum of cosine basis patterns — one DC term (the block average) plus 63 AC terms of rising frequency. The DCT itself is lossless and compresses nothing; what it does is concentrate energy into the top-left corner. Quantization — dividing by a table and rounding — is where the loss actually occurs, and the "quality" slider is nothing more than a scale factor applied to that table.
🔒 BUILD: Implement the 8×8 DCT-II and its inverse. Round-trip a block and confirm you get it back within float error. Then quantize with the standard JPEG luma table at several quality levels and watch the high-frequency coefficients collapse to zero — that's compression happening in front of you.
WEDNESDAY — ENTROPY CODING (2.5 HRS)
📗 LEARN: After quantization the block is mostly zeros. Zigzag ordering walks the block so those zeros end up contiguous at the tail, run-length encoding collapses the runs, and Huffman coding assigns short bit patterns to frequent symbols. Huffman construction is a greedy algorithm over a min-heap: repeatedly merge the two least-frequent nodes.
🔒 BUILD: Huffman from scratch in Rust — `BinaryHeap` with `Reverse` for the min-heap, code assignment by tree walk, then encode and decode. Verify a round-trip on your quantized coefficients and report the compression ratio you achieved.
🎯 INTERVIEW: This is a greedy + heap + tree problem you can now discuss with a real application attached, which is far stronger than reciting it from a DSA deck. Know the contrast too: JPEG uses Huffman, modern codecs use arithmetic or range coding (better ratio, more CPU), and PNG uses DEFLATE — LZ77 plus Huffman — after per-row prediction filters.
THURSDAY — MODERN FORMATS & THE REAL TRADEOFF (2.5 HRS)
📗 LEARN: What changed since 1992 — WebP (VP8 intra frames), AVIF (AV1 intra: much better at low bitrate, much slower to encode), JPEG XL (technically excellent, patchy support), and lossless PNG versus lossy everything. The engineering question is never "which format is best" but "which do I encode, at what CPU cost, for which client" — encode cost is paid once, bytes are paid on every single request, and support is negotiated per request through the Accept header.
🎯 INTERVIEW: The Netflix-flavored version worth knowing — per-title and per-shot encoding. A fixed bitrate ladder wastes bits on simple content and starves complex content, so you derive the ladder per asset from a rate-distortion curve instead. The same logic applies to picking a per-image quality parameter rather than hardcoding q=85 everywhere, which is what almost everyone does.
FRIDAY — QUALITY METRICS (2.5 HRS)
📗 LEARN: PSNR is trivial to compute and correlates weakly with what people actually see. SSIM compares local luminance, contrast, and structure, and does noticeably better. VMAF is Netflix's own open-source metric — a model trained on human ratings that fuses several elementary metrics. All of them can be gamed by an encoder tuned against them, which is precisely why encoding teams still run human trials.

📗 LEARN: The wasm-bindgen guide. Crossing JS↔WASM costs real time: strings are re-encoded (UTF-8 ↔ UTF-16) and values are copied. For image data the fix is to stop crossing it — allocate the pixel buffer INSIDE WASM linear memory, hand JavaScript a `Uint8ClampedArray` view over that memory, and let JS read and write the view directly. Zero copies in either direction. Meet js-sys (JS builtins) and web-sys (DOM and Web APIs).
