The ownership invariant

Every other language manages memory in one of two ways: garbage collection (JVM, Python, Go — pay a runtime cost; the GC finds unreachable memory) or manual allocation (C, C++ — you call free; you can get it wrong). Rust does neither. Instead it encodes a single compile-time rule:

⚡

Every value has exactly one owner at a time. When the owner goes out of scope, the value is dropped (freed) — automatically, with no runtime cost.

From that one rule, the borrow checker — a static analysis pass in the compiler — can prove at compile time that your program is free of use-after-free bugs, double-frees, data races, and dangling pointers. No runtime overhead, no GC pauses.

The three rules (memorise these)
Rule 1 Each value in Rust has exactly one owner. Rule 2 When the owner goes out of scope, the value is dropped. Rule 3 (borrowing) At any given time you may have EITHER: • any number of shared references &T (read-only) • exactly ONE mutable reference &mut T (read+write) Never both at the same time.

Rule 3 is why Rust eliminates data races: a data race requires concurrent mutable access. The borrow checker makes that illegal even in single-threaded code — and then the same type system propagates the guarantee to threads via the Send and Sync marker traits.

Everything else in the language — lifetimes, smart pointers, Arc<Mutex<T>>, the async model — is the type system finding ways to express valid programs that stay within these rules.

Cargo & the Rust edition model

Cargo is Rust's build system and package manager — think npm + webpack + pip rolled into one. A Cargo project is defined by Cargo.toml:

# Cargo.toml — every project starts here
[package]
name    = "hello-rust"
version = "0.1.0"
edition = "2024"   # language edition — use 2024 for new projects

[dependencies]
# crates from crates.io go here, e.g.:
anyhow = "1"

Key editions: Rust ships a new edition every 3 years. Edition 2024 (stabilised early 2025) is the current default. Editions are per-crate opt-in — your code and a dependency can be different editions; the compiler handles it. The main 2024 changes relevant to you: async fn in traits is now stable without extra crates, and extern "C" functions now implicitly require unsafe at the call site.

Why the compiler errors are famously good

rustc's error messages are designed to be the tutorial. When the borrow checker rejects your code it usually tells you exactly which rule was violated, shows you the conflicting borrows, and often suggests the fix. Ownership, Borrowing & Lifetimes
The make-or-break week · everything else depends on this
The whole week is one concept approached from different angles. Don't rush past confusion — if something doesn't click, that's signal to re-read, not to move on.
Move semantics vs Copy vs Clone

Rust types fall into two categories based on the Copy trait:

CategoryTypesWhat happens on assignment / function call
Copyall integers, floats, bools, char, tuples of Copy types, &T referencesA bitwise copy is made. Original still valid. No overhead.
Move (not Copy)String, Vec<T>, Box<T>, your structsOwnership transfers. Original is moved out and can no longer be used. Prevents double-free.
let x: i32 = 5;
let y = x;       // Copy — x still valid, y gets its own copy
println!("{} {}", x, y); // fine

let s1 = String::from("hello");
let s2 = s1;       // MOVE — s1 no longer owns the data
// println!("{}", s1); ← COMPILE ERROR: value used after move
println!("{}", s2); // fine — s2 is the owner now

let s3 = s2.clone(); // explicit deep copy — now both s2 and s3 are valid
⚠

Don't reach for .clone() to fix every borrow error — it's often the right tool, but when you find yourself cloning frequently it usually means you should be borrowing instead. Over-cloning is idiomatic to beginners and a red flag in interviews.

Borrowing — the aliasing rule in one picture

A reference lets you use a value without taking ownership. References are always valid — the compiler guarantees no dangling references.

fn length(s: &String) -> usize {  // borrows s, does NOT take ownership
    s.len()
}  // s goes out of scope here, but it's a borrow — nothing is dropped

let mut s = String::from("hello");
let len = length(&s);   // shared borrow — s is still the owner
s.push_str(", world");  // fine — mutable access after shared borrow ended
At any moment, for a given value, you may have: Multiple shared (&T) OR Exactly one mutable (&mut T) read-only, any count full access, exclusive NEVER both simultaneously This maps directly onto a readers/writer lock: multiple readers = OK • one writer, no readers = OK • both = ERROR

This rule means: if you see a compile error about "cannot borrow as mutable because it is also borrowed as immutable", draw the timeline: find where the shared borrow starts and ends, and see if your mutable borrow overlaps. Usually the fix is restructuring the borrow scopes.

&str vs String — the #1 early friction point
TypeWhere it livesUse in
&strBorrowed slice — could point into a String, a string literal, or anywhereFunction parameters. Prefer &str over &String — it's strictly more flexible.
StringHeap-allocated, owned, growableReturn values you're constructing. Fields that need to own their data.

Golden rule: functions that just read a string should take &str. Callers can pass either a &str literal or a &String (which auto-derefs to &str).

Lifetimes — labels, not durations

Lifetimes are the compiler's notation for expressing which reference came from where. They exist to prevent dangling references. The crucial insight: lifetimes don't change how long values live — they only describe relationships between references so the compiler can verify safety.

// Without explicit lifetime: compiler can't verify the return reference is valid
// The question: does the returned &str point into s1 or s2?
fn longest<'a>(s1: &'a str, s2: &'a str) -> &'a str {
    // 'a means: "the return value lives at least as long as the shorter of s1 and s2"
    if s1.len() > s2.len() { s1 } else { s2 }
}
💡

Lifetime elision rules: most functions don't need explicit lifetime annotations because the compiler applies three inference rules. You only write 'a when the rules are ambiguous — typically when a function returns a reference derived from multiple input references, as above. If your function takes one reference input and returns a reference, elision handles it.

Watch Jon Gjengset's Crust of Rust: Lifetime Annotations — it's the single best explanation. Plan on watching it twice.

Enums, Option and match

Rust enums are algebraic data types — each variant can carry different data. Option<T> is just an enum with two variants: Some(T) and None. It replaces null. The compiler forces you to handle both cases.

// A data-carrying enum (Shape for the plan's Saturday project)
enum Shape {
    Circle(f64),           // carries radius
    Rectangle(f64, f64),  // carries width, height
}

impl Shape {
    fn area(&self) -> f64 {
        match self {
            Shape::Circle(r)       => 3.14159 * r * r,
            Shape::Rectangle(w, h) => w * h,
        }
    }
}

// Option — every value that might not exist
fn divide(a: f64, b: f64) -> Option<f64> {
    if b == 0.0 { None } else { Some(a / b) }
}

// if let — concise single-arm match
if let Some(result) = divide(10.0, 3.0) {
    println!("Result: {result:.2}");
}
Week 1 interview framing
Interview Q

What problem does Rust's ownership system solve, and why doesn't it need a GC?

Answer: Memory safety bugs (use-after-free, double-free, data races) are the most common class of CVEs in C/C++ codebases. GC solves this but imposes runtime overhead and nondeterministic pauses. Rust instead encodes ownership as a type-level invariant verified at compile time — one owner, one drop — so the compiler can insert frees automatically, like a GC but at zero runtime cost. The borrow checker extends this to prevent concurrent mutable access without runtime locks.

Generics & monomorphization

Generics let you write code parameterised over types. Unlike Java generics (which use type erasure at runtime), Rust uses monomorphization: the compiler generates a separate copy of the function for each concrete type it's called with. Zero runtime overhead — the cost of abstraction is paid entirely at compile time.

// A generic function with a trait bound
fn largest<T: PartialOrd>(list: &[T]) -> &T {
    let mut largest = &list[0];
    for item in list {
        if item > largest { largest = item; }
    }
    largest
}
// Compiler creates: largest_i32, largest_f64, etc. No vtable, no boxing.
Traits — Rust's interfaces

A trait defines shared behaviour. Any type can implement any trait. This is Rust's primary polymorphism mechanism, and it's where the language's power comes from.

trait Area {
    fn area(&self) -> f64;
    fn describe(&self) -> String {  // default method
        format!("Area: {:.2}", self.area())
    }
}
impl Area for Circle {
    fn area(&self) -> f64 { 3.14159 * self.radius.powi(2) }
}

The essential derives

#[derive(...)] is a proc-macro that auto-implements standard traits:

Debug + Display

#[derive(Debug)] enables {:?} formatting. For user-facing output implement Display manually. Always derive Debug on your types.

Clone + Copy

Clone: opt-in deep copy via .clone(). Copy (requires Clone): makes the type implicitly bitwise-copyable — no move. Only for small stack types.

PartialEq + Eq + Hash

PartialEq: == and !=. Eq: total equality (no NaN-like weirdness). Hash: required to use your type as a HashMap key — requires Eq.

Default

Default: provides T::default(). Useful for builder patterns and struct initialization. Common to derive alongside Debug.

Error handling — the Rust way

Rust has no exceptions. Errors are values. The type system forces you to handle them. This removes whole categories of bugs (uncaught exceptions in prod).

The two core types: Option<T> for "might not exist" and Result<T, E> for "might fail".

// The ? operator: early-return on error, propagating upward
fn read_username() -> Result<String, std::io::Error> {
    let mut s = String::new();
    std::fs::File::open("user.txt")?.read_to_string(&mut s)?;
    // ? desugars to: match result { Ok(v) => v, Err(e) => return Err(e.into()) }
    Ok(s)
}

For real projects, use the ecosystem crates:

CrateForHow
thiserrorLibraries — define your error type#[derive(thiserror::Error)] on an enum; each variant gets a message. Keeps your public API clean.
anyhowApplications — propagate any errorResult<T, anyhow::Error> in your main / handlers. Any error can be converted automatically.
// thiserror — define your error enum (used in libraries)
use thiserror::Error;
#[derive(Debug, Error)]
enum TokenizeError {
    #[error("unexpected character: {0}")]
    UnexpectedChar(char),
    #[error("unterminated string literal at position {pos}")]
    UnterminatedString { pos: usize },
}
HashMap from scratch — the Week 2 project

This is your centerpiece portfolio project. Building it teaches every Week 2 concept in combination: generics (K, V), trait bounds (K: Hash + Eq), ownership (who owns the keys and values), and error handling (index out of bounds).

use std::collections::hash_map::DefaultHasher;
use std::hash::{Hash, Hasher};

struct MyHashMap<K, V> {
    buckets: Vec<Vec<(K, V)>>,
    len: usize,
}

impl<K: Hash + Eq, V> MyHashMap<K, V> {
    fn new() -> Self {
        let cap = 16;
        Self { buckets: (0..cap).map(|_| Vec::new()).collect(), len: 0 }
    }

    fn bucket_index(&self, key: &K) -> usize {
        let mut h = DefaultHasher::new();
        key.hash(&mut h);
        (h.finish() as usize) % self.buckets.len()
    }

    fn insert(&mut self, key: K, val: V) {
        if self.load_factor() > 0.75 { self.rehash(); }
        let idx = self.bucket_index(&key);
        // if key exists, overwrite; otherwise push
        for (k, v) in &mut self.buckets[idx] {
            if k == &key { *v = val; return; }
        }
        self.buckets[idx].push((key, val));
        self.len += 1;
    }
    // load_factor, get, remove, rehash left as exercise
}
ℹ

The real std::collections::HashMap uses Robin Hood hashing (open addressing) with the hashbrown library under the hood. Your chaining implementation is simpler and easier to reason about for learning — and understanding the tradeoffs (chaining vs open addressing, load factor, worst-case O(n) vs amortised O(1)) is exactly what an interviewer wants to probe.

Closures & the Iterator trait

Rust's iterators are lazy: a chain like .map().filter() creates no intermediate collections — it describes a sequence of operations to be run only when consumed by a collect(), for, sum(), etc. This makes idiomatic Rust faster than equivalent loop code, not slower.

let numbers = vec![1, 2, 3, 4, 5];

// Imperative style — allocates a new Vec for each step
let mut evens = Vec::new();
for n in &numbers {
    if n % 2 == 0 { evens.push(n * 2); }
}

// Iterator style — lazy, one pass, zero intermediate Vecs
let evens: Vec<_> = numbers.iter()
    .filter(|&&n| n % 2 == 0)
    .map(|&n| n * 2)
    .collect();  // type annotation drives collect() — it returns Vec, HashSet, String, etc.

The three iterator methods you'll reach for constantly:

Transforming

.map(f) — transform each element
.flat_map(f) — map then flatten
.enumerate() — add index
.zip(other) — pair with another iterator

Filtering

.filter(pred) — keep matching elements
.filter_map(f) — map + filter in one pass
.take(n) / .skip(n)
.take_while(pred)

Consuming (terminators)

.collect::<T>() — into any collection
.fold(init, f) / .reduce(f)
.sum() / .product()
.count() / .any() / .all()

Fn traits (closures)

Fn — borrows env, callable many times
FnMut — mutably borrows, may modify env
FnOnce — consumes env, calls once
Rust infers the right variant automatically.

Smart pointers — Box, Rc, RefCell

The ownership system is strict: one owner, one mutable reference. Sometimes you legitimately need to escape these constraints. Smart pointers are the principled escape hatches.

TypeWhat it gives youWhen to use
Box<T>Heap allocation. Single owner. No runtime overhead beyond the indirection.Large data you don't want on the stack. Recursive types (e.g. linked list). Trait objects (Box<dyn Trait>).
Rc<T>Reference-counted shared ownership. Multiple owners. Single-threaded only.Graph structures. UI trees. Anything where multiple parts of the code need shared read access in a single thread.
Arc<T>Atomic Rc — thread-safe shared ownership. Slightly more expensive than Rc due to atomic ops.Same use cases as Rc but across threads. The A stands for Atomic.
RefCell<T>Interior mutability: moves borrow checking from compile time to runtime. Use .borrow() / .borrow_mut(). Panics if rules violated.When you need to mutate through a shared reference. Often paired as Rc<RefCell<T>>.
Mutex<T>Interior mutability across threads. Blocks until lock acquired.Shared mutable state across threads. Pair with Arc: Arc<Mutex<T>>.
// Recursive type requires Box — otherwise infinite size
enum List {
    Cons(i32, Box<List>),  // Box breaks the recursive size problem
    Nil,
}

// Shared mutable state (single-threaded)
let shared = Rc::new(RefCell::new(vec![1, 2, 3]));
let clone1 = Rc::clone(&shared);
clone1.borrow_mut().push(4);  // runtime borrow check — panics if already borrowed
⚡

Never hold a std::sync::Mutex lock across an .await point in async code — the lock might be held while the thread is running other tasks, causing a deadlock. Use tokio::sync::Mutex instead for async contexts (Week 4).

Modules, crates & workspaces

The Rust module system maps directly to the filesystem:

src/
  main.rs          ← binary root; declares modules
  lib.rs           ← library root (if a dual crate)
  hashmap/
    mod.rs         ← OR: src/hashmap.rs for a single-file module
    bucket.rs      ← sub-module

// In main.rs:
mod hashmap;           // loads src/hashmap/mod.rs or src/hashmap.rs
use hashmap::MyHashMap; // bring into scope

// Visibility:
pub fn public_fn()   {}   // visible outside the module
pub(crate) fn internal() {} // visible within this crate only
fn private_fn()      {}   // private to this module

A crate is a compilation unit (a library or binary). A workspace is a Cargo.toml at the root listing multiple crates — useful when your project grows beyond one crate.

Documentation comments: use /// for item docs and //! for module/crate docs. They support Markdown. Run cargo doc --open to see rendered docs. Writing good /// doc comments with example code blocks is a real professional signal.

Concurrency & Async Foundations
Threads, Send/Sync, async/await, Tokio
Phase 2 is where the Phase 1 theory pays off. The ownership model directly enables fearless concurrency — data races become compile errors.
OS threads & shared state

Rust's threading model is standard OS threads, not green threads. The ownership system's constraint on &mut references means sharing mutable data between threads requires explicit synchronisation primitives — and the type system enforces it.

use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0));
let mut handles = vec![];

for _ in 0..10 {
    let c = Arc::clone(&counter);
    handles.push(thread::spawn(move || {  // `move` captures c by value
        let mut n = c.lock().unwrap();    // acquire lock — blocks until available
        *n += 1;                           // lock released when `n` drops
    }));
}
for h in handles { h.join().unwrap(); }
println!("counter = {}", *counter.lock().unwrap()); // 10
Send and Sync — the thread safety markers
TraitMeaningImplemented by
SendSafe to move ownership to another threadAlmost everything except Rc (non-atomic ref count) and raw pointers
SyncSafe to share a reference across threads (i.e. &T is Send)Everything that has no interior mutability, or uses thread-safe interior mutability (Mutex)

Rc is not Send — if you try to send an Rc to a thread the compiler rejects it. This is why Arc exists. These traits are checked by the compiler: if your type contains any non-Send field, your type won't be Send either — automatically propagated.

The async/await model

OS threads are expensive (8 MB stack each; kernel context-switch). For I/O-bound work (waiting on network, disk) most of that time is just waiting. Async lets you run millions of concurrent tasks on a handful of OS threads by suspending waiting tasks and running ready ones.

The key mental model for Rust async:

async fn fetch_data() -> String { ... } Does NOT execute immediately. Returns a Future<Output = String> — a state machine that knows how to make progress when polled. Futures are LAZY. Nothing runs until a runtime polls the Future. Timeline: call async fn → get a Future (no work done) .await → "drive this Future to completion; yield if it's waiting" runtime polls → Future runs until it would block, then suspends
// async fn creates a Future (a state machine)
async fn fetch_url(url: &str) -> String {
    let body = reqwest::get(url).await.unwrap()
        .text().await.unwrap();
    body  // .await suspends here while waiting for the HTTP response
}     // during that wait, the runtime can run OTHER futures on the same thread

// Run multiple concurrently with tokio::join!
let (a, b) = tokio::join!(fetch_url("http://a.com"), fetch_url("http://b.com"));
// Both are running concurrently — the runtime interleaves them at .await points
Tokio — the async runtime

The Rust standard library defines the Future trait but provides no runtime. Tokio is the de-facto standard runtime (as of 2025, async-std is effectively deprecated). Tokio provides: an async task scheduler, async I/O (TCP, UDP, files), timers, and sync primitives.

// #[tokio::main] expands to: set up the runtime, run this async fn, block until done
#[tokio::main]
async fn main() {
    // tokio::spawn — fire-and-forget task (like a thread but cheap)
    let handle = tokio::task::spawn(async {
        // runs concurrently
    });

    // tokio::select! — race multiple futures, take the first to complete
    tokio::select! {
        result = some_future() => { ... }
        _ = tokio::time::sleep(Duration::from_secs(5)) => { eprintln!("timeout"); }
    }

    handle.await.unwrap();
}
tokio::sync::mpsc

Multi-producer, single-consumer channel. Use for sending work from many tasks to one consumer. Prefer over std::sync::mpsc in async code.

tokio::sync::broadcast

One sender, many receivers — each gets every message. Perfect for the Week 4 chat server: broadcast incoming messages to all connected clients.

tokio::sync::Mutex

Like std Mutex but .await-aware. Use when you need to hold a lock across an .await point. Otherwise std::sync::Mutex is fine (and faster).

tokio::time

sleep(Duration), timeout(dur, future), interval(dur). Essential for retry logic, health checks, and any time-bounded operation.

Interview Q

Why are Rust futures lazy? What does this enable?

Answer: A future only runs when polled by a runtime. This means constructing a future is zero-cost — no work begins until you explicitly drive it. This enables: composing futures without running them (chaining with combinators), cancellation by simply dropping a future, and efficient runtimes that only poll futures that have registered a wakeup (no busy-waiting). Contrast with eager async (e.g. JS Promises), where the work starts immediately on construction.

axum — the modern Rust web framework

axum (from the Tokio team) is built on hyper and tower. Its design is type-driven: handlers are async functions whose arguments are extractors — types that parse the request. If a request can't satisfy the extraction, axum returns a 400 automatically.

use axum::{routing::{get, post}, Router, Json, extract::{Path, State}};
use std::sync::Arc;

#[tokio::main]
async fn main() {
    let state = Arc::new(AppState::new());

    let app = Router::new()
        .route("/health", get(health_handler))
        .route("/users/:id", get(get_user))
        .route("/users", post(create_user))
        .with_state(state);

    axum::serve(tokio::net::TcpListener::bind("0.0.0.0:3000").await.unwrap(), app)
        .await.unwrap();
}

// Extractors in the signature: axum parses them automatically
async fn get_user(
    Path(id): Path<u64>,          // extracts :id from path
    State(state): State<Arc<AppState>>,  // shared application state
) -> Json<User> {
    Json(state.find_user(id).await)
}
serde — serialization/deserialization

serde is arguably the most important library in the Rust ecosystem. It defines a serialization data model (a set of types that any format can map to/from) and uses proc-macros to generate efficient ser/de code at compile time. Zero runtime reflection — it's all code gen.

use serde::{Deserialize, Serialize};

#[derive(Debug, Serialize, Deserialize)]
struct User {
    id: u64,
    name: String,
    #[serde(skip_serializing_if = "Option::is_none")]  // omit from JSON if None
    email: Option<String>,
    #[serde(rename = "created_at")]                   // different JSON key name
    created: u64,
}

// Serialize to JSON string
let json = serde_json::to_string(&user)?;

// Deserialize from JSON bytes (e.g. from an HTTP body)
let user: User = serde_json::from_slice(&body_bytes)?;

// axum's Json extractor does this automatically — the type annotation is the instruction
async fn create_user(Json(payload): Json<CreateUserRequest>) -> ... { ... }
sqlx — compile-time checked SQL

sqlx's key selling point: the query! and query_as! macros verify your SQL against the actual database schema at compile time. Typos in column names become compiler errors, not runtime panics in production.

// sqlx with SQLite — set DATABASE_URL env var for compile-time check
use sqlx::SqlitePool;

async fn get_user_by_id(pool: &SqlitePool, id: i64) -> sqlx::Result<User> {
    // query_as! maps rows directly to your struct — column names must match field names
    sqlx::query_as!(User, "SELECT id, name, email FROM users WHERE id = ?", id)
        .fetch_one(pool)
        .await
}

// Migrations live in migrations/ directory, run via sqlx-cli or at startup:
sqlx::migrate!().run(&pool).await?;  // applies pending migrations
ℹ

The compile-time query check requires a real database to be present during compilation (or a cached .sqlx/ directory). Set DATABASE_URL in your .env file and run sqlx prepare before CI to cache the checks offline.

What WebAssembly is and why Rust

WebAssembly (WASM) is a binary instruction format that runs in a sandboxed virtual machine. Browsers, Node.js, and standalone runtimes can execute it. It's not a replacement for JavaScript — it's a compilation target for languages that need predictable performance in environments that can run WASM.

JavaScriptRust-WASM
StartupFast; JIT-compiled over timeSlightly slower initial parse; then predictable
Peak perfJIT good but GC pauses visiblePredictable, no GC — often 2–5× faster for compute-heavy tasks
Binary sizeN/A (not shipped as binary)~50 KB–2 MB depending on deps and opt level
Sweet spotDOM manipulation, light logicImage/video processing, parsers, cryptography, physics, compression

Rust is the top WASM language because: no runtime to ship (no GC, no allocator overhead by default), tiny binaries, excellent wasm-bindgen tooling, and the safety guarantees carry over to the browser context.

wasm-bindgen — the JS↔Rust bridge

wasm-bindgen generates the glue code that lets JavaScript call Rust functions and vice versa. The boundary is the key concept to understand: crossing the JS↔WASM boundary has a cost because WASM's linear memory and JavaScript's heap are separate. Every value that crosses the boundary must be copied and potentially converted (Rust's UTF-8 strings vs JS's UTF-16).

use wasm_bindgen::prelude::*;

// Exported to JavaScript
#[wasm_bindgen]
pub fn greet(name: &str) -> String {
    format!("Hello, {}!", name)
}

// Export a struct with methods
#[wasm_bindgen]
pub struct ImageProcessor { data: Vec<u8> }

#[wasm_bindgen]
impl ImageProcessor {
    #[wasm_bindgen(constructor)]
    pub fn new(width: u32, height: u32) -> Self { ... }

    // Takes a JS Uint8Array by passing a pointer into WASM memory
    pub fn grayscale(&mut self) { ... }

    // Returns pointer to internal buffer — JS reads directly, no copy
    pub fn as_ptr(&self) -> *const u8 { self.data.as_ptr() }
}
💡

Minimise boundary crossings. Instead of calling a Rust function per pixel, pass the entire image buffer once, let Rust process it, and read the result back once. The cost of one coarse-grained call vastly outweighs many fine-grained ones.

WASI — WASM beyond the browser

WASI (WebAssembly System Interface) is a standard set of syscalls that gives WASM modules sandboxed access to the host: files, environment variables, clocks, sockets. The promise: compile once, run sandboxed anywhere that has a WASI runtime.

WASI preview1 (wasip1)WASI preview2 (wasip2)
StatusTier 2 stable in Rust — wasm32-wasip1Tier 2 — wasm32-wasip2
NetworkingFiles/env only, no socketsAdds sockets (WASI sockets spec)
UseCLI tools, serverless, pluginsNetwork services, edge compute
# Compile a CLI to WASI
rustup target add wasm32-wasip1
cargo build --target wasm32-wasip1 --release

# Run with Wasmtime
wasmtime target/wasm32-wasip1/release/my-cli.wasm -- --help
# Sandboxed: Wasmtime controls what files/env the WASM module can see
The Component Model — portable plugins

Plain WASM modules communicate only through integers and floats. The Component Model adds a rich type system for the interface: strings, records, enums, options, results — described in WIT (WebAssembly Interface Types) files. This enables a WASM component written in Rust to call a component written in Go, with no shared runtime.

// my-interface.wit — define the component's public API
package my:example;
interface greeter {
    greet: func(name: string) -> string;
}
world my-world {
    export greeter;
}

// cargo component (cargo install cargo-component) generates Rust bindings
// then you implement the generated trait:
impl Guest for MyComponent {
    fn greet(name: String) -> String { format!("Hello, {}!", name) }
}

Why this matters for your backend interest: you can build a Rust HTTP service that accepts user-submitted .wasm plugins and executes them sandboxed via Wasmtime. This is how plugin systems at companies like Fastly (Compute@Edge) and Cloudflare (Workers) work. It's the most impressive portfolio project in the plan.

Macros — code that writes code

Rust has two kinds of macros. Understanding the difference is important before Week 7:

Declarative (macro_rules!)Procedural (proc-macros)
MechanismPattern matching on token trees — like regex but for code structureA Rust program that runs at compile time, receives a token stream, returns a new token stream
Powersvec![...], println!, test-case generators, mini-DSLs#[derive(Serialize)], #[tokio::main], custom attributes
Key cratesNone (built-in)proc-macro2, syn (parse), quote (generate)
// A declarative macro — HashMap literal
macro_rules! hashmap {
    ( $( $key:expr => $val:expr ),* $(,)? ) => {{
        let mut m = std::collections::HashMap::new();
        $( m.insert($key, $val); )*
        m
    }};
}
// Usage:
let scores = hashmap! { "Alice" => 95, "Bob" => 87 };
// A proc-macro derive crate (separate crate, proc-macro = true in Cargo.toml)
use proc_macro::TokenStream;
use quote::quote;
use syn::{parse_macro_input, DeriveInput};

#[proc_macro_derive(HelloMacro)]
pub fn hello_macro_derive(input: TokenStream) -> TokenStream {
    let ast = parse_macro_input!(input as DeriveInput);
    let name = &ast.ident;
    quote! {
        impl HelloMacro for #name {
            fn hello() { println!("Hello from {}!", stringify!(#name)); }
        }
    }.into()
}

unsafe Rust — the five superpowers

The common misconception: unsafe turns off the borrow checker. It doesn't. What unsafe does is grant five specific abilities that the compiler cannot verify, while holding you responsible for upholding the invariants. The borrow checker still runs inside unsafe blocks — it just additionally permits these five things:

  • Dereference raw pointers (*const T, *mut T) — could be dangling or misaligned
  • Call unsafe functions — functions that require invariants the caller must guarantee
  • Implement unsafe traits — Send, Sync (the compiler can't prove thread safety automatically)
  • Mutate statics — mutable global state, inherently racy if not synchronised
  • Access fields of unions — only one field is valid at a time; the compiler can't know which
// Example: split_at_mut — requires unsafe because two &mut slices to the same buffer
fn split_at_mut(slice: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    let ptr = slice.as_mut_ptr();
    // SAFETY: mid <= slice.len(), and the two slices are non-overlapping
    unsafe {
        (
            std::slice::from_raw_parts_mut(ptr, mid),
            std::slice::from_raw_parts_mut(ptr.add(mid), slice.len() - mid),
        )
    }
}
⚠

Always document your safety invariant with a // SAFETY: ... comment above every unsafe block. Explain why the operations are valid given the context. This is not style — it's the professional contract between the unsafe code author and future maintainers.

FFI — Foreign Function Interface

FFI lets Rust interoperate with C (the lingua franca of native code) and Python (via PyO3). Everything across the FFI boundary is unsafe because Rust can't verify the calling conventions, lifetimes, or invariants of external code.

// Calling C from Rust
extern "C" {
    fn abs(x: i32) -> i32;  // declaration of a C function
}
fn main() {
    unsafe { println!("{}", abs(-3)); }  // unsafe because Rust can't verify C's behaviour
}

// Exposing Rust to C (extern "C" now requires unsafe in 2024 edition)
#[no_mangle]  // don't mangle the symbol name — C needs to find it by exact name
pub unsafe extern "C" fn rust_add(a: i32, b: i32) -> i32 { a + b }

// PyO3 — Rust extension modules for Python
// [lib] crate-type = ["cdylib"] in Cargo.toml, plus pyo3 = { version = "0.23", features = ["extension-module"] }
use pyo3::prelude::*;
#[pyfunction]
fn fast_sum(data: Vec<f64>) -> f64 { data.iter().sum() }
#[pymodule]
fn my_module(m: &Bound<PyModule>) -> PyResult<()> { m.add_function(wrap_pyfunction!(fast_sum, m)?)?; Ok(()) }
Performance — making Rust fast

Rust code is already fast by default. The main things that slow it down are unnecessary allocations and clones. The performance principles in order of impact:

  • Use &str over String and &[T] over Vec<T> in function parameters — avoid a clone just to call a function
  • Prefer iterators over manual loops — the compiler can vectorise and optimise iterator chains better
  • Release builds — cargo build --release can be 10–100× faster than debug. Never benchmark debug builds.
  • Profile before optimising — cargo flamegraph shows you where time is actually spent
  • Criterion for benchmarks — statistically rigorous, measures wall time with warmup
// criterion benchmark (in benches/my_bench.rs)
use criterion::{criterion_group, criterion_main, Criterion};

fn bench_hashmap(c: &mut Criterion) {
    c.bench_function("1M inserts", |b| {
        b.iter(|| {
            let mut m = MyHashMap::new();
            for i in 0..1_000_000 { m.insert(i, i); }
        });
    });
}
criterion_group!(benches, bench_hashmap);
criterion_main!(benches);

Quick reference: things people get wrong
Common misconceptions and the corrections
Common mistake

"I'll clone() to fix the borrow error" — correct in the short term, but overuse signals that you haven't internalised borrowing. Fix the lifetime instead.

Common mistake

Using String in function parameters instead of &str. Any function that just reads a string should take &str — the caller can pass either &str or &String.

Common mistake

Holding a std::sync::Mutex guard across an .await. This can deadlock the executor. Use tokio::sync::Mutex or drop the guard before the await.

Common mistake

Benchmarking in debug mode. cargo bench and flamegraph should always run against --release. Debug builds can be 10–100× slower and don't represent real performance.

Common mistake

Using Rc when you need thread-safety. Rc is single-threaded. If the type crosses thread boundaries (spawn), the compiler rejects it — use Arc instead.

Common mistake

Thinking unsafe disables the borrow checker. It doesn't — it only grants 5 specific additional capabilities. The borrow checker is still active; you just also gain the ability to dereference raw pointers etc.
